# Phase 3 TDD Implementation Plan Review

## Verdict

**REVISE — production Phase 3 implementation is not yet authorized.**

The plan is substantially stronger than the prior phases and correctly maps the approved visual-fidelity design into staged TDD work. It preserves the single scientific source of truth, privacy boundary, asymmetric exemplar roles, one PPTX backend, fresh-template reconstruction, reconstruction metrics, and independent native-PowerPoint gate.

However, the implementation plan still contains several plan-level assumptions that can create false professor-fidelity PASS or unnecessary private-data exposure. These must be corrected before production code is authorized.

## Accepted portions

The following planning decisions are approved and should not regress:

- privacy tests and ignored-root guard precede any private PPTX profiling;
- the private profiler is data-minimized and sanitizer output is fail-closed;
- Exemplar 1/3 govern shell token families and Exemplar 2 cannot supply shell tokens;
- shell conflict records preserve winning source, losing alternative, rule ID, and classification;
- A01–A18 semantic contracts remain immutable across visual calibration;
- Fishbone calibration changes style only, not canonical graph/history;
- reconstructed PPTX is built fresh through `PythonPptxAssembler` only;
- private reference renders and private package evidence remain local-only;
- quantitative reconstruction metrics are independent gates, not replaced by global pixel similarity;
- the acceptance deck remains Ledger-derived after `Ledger.load()`;
- native PowerPoint remains a separate blocked gate when unavailable.

## Blocking corrections

### P3-PLAN-B1 — Image-capable review must use a capability abstraction and preflight

The plan states that the implementation environment exposes `functions.view_image(detail=original)` and builds the runtime design around that exact tool name.

Tool availability is a runtime capability, not a repository invariant. The production plan must not hard-code one agent-tool symbol as if guaranteed.

Required correction:

- define an `ImageReviewProvider`/equivalent capability contract;
- perform an explicit capability preflight before any private visual-classification run;
- record provider ID, capability level, supported image path/input form, and hash-binding support;
- the Codex-specific implementation may use `functions.view_image` when available, but durable modules/contracts depend on the provider abstraction rather than the literal tool name;
- if no image-capable provider is available, qualitative classification/review becomes `blocked_visual_review` and cannot silently fall back to metadata or pixel heuristics;
- private profiling may continue for purely structural measurements, but any work requiring qualitative visual classification must remain blocked.

Add RED tests for unavailable provider, non-image provider, provider that cannot bind the inspected render hash, and stale/mismatched review input.

### P3-PLAN-B2 — One descriptor is not sufficient evidence for class-level archetype calibration

The plan currently allows most A01–A18 archetypes to become calibrated from a minimum of one descriptor. One slide can be an idiosyncratic outlier and does not establish a professor-wide composition grammar.

Required correction:

Introduce explicit calibration evidence tiers, for example:

- `recurring_pattern`: >=2 independent direct descriptors with compatible geometry/style evidence;
- `single_example_provisional`: exactly one direct descriptor;
- `indirect_supported`: no direct descriptor but explicitly mapped support from a closely related approved family;
- `insufficient_evidence`: no defensible evidence.

Keep separate statuses for:

1. `acceptance_deck_fidelity` — whether the specific generated acceptance slides match their selected references; and
2. `archetype_library_calibration_coverage` — whether the reusable A01–A18 library is generally calibrated.

A single-example archetype may be benchmarked as a single-example reconstruction, but must not be presented as recurring professor grammar unless an explicit reviewer waiver exists.

No automatic reviewer waiver may be generated by the builder.

### P3-PLAN-B3 — Reconstruction benchmark must test representative and stress examples

The current deterministic selector chooses the descriptor with the greatest slot count, then highest annotation density. This is useful as a stress test but can select an unusual outlier and overfit the system away from the professor's normal visual grammar.

Required correction:

For each family with enough evidence, choose at least two benchmark roles:

- `representative_reference`: the descriptor closest to the family medoid/modal composition in sanitized metric space;
- `stress_reference`: the high-complexity/high-density descriptor.

If only one descriptor exists, mark the benchmark `single_example` and do not infer family recurrence.

Persist selection rationale and sanitized distance/complexity metrics. Reconstruction fidelity must not pass a family solely from a stress outlier or solely from an easy representative.

### P3-PLAN-B4 — Zero private-part hash equality is not a valid universal non-reuse criterion

The plan currently requires `equal-hash count == 0` between every private source package part and every reconstructed package part.

Freshly generated standard OOXML boilerplate can legitimately be byte-identical to a private source part (for example deterministic standard package metadata/content-type/relationship structures). Hash equality alone cannot distinguish copying from independent deterministic generation and can create false failures.

Required correction:

Use a stronger lineage/non-reuse proof:

- the reconstruction API may accept sanitized descriptors only and must have no private path/package parameter;
- persist a reconstruction lineage manifest identifying the sanitized descriptor(s) and builder-generated origin of every output part;
- classify output/source part comparisons into at least `prohibited_content_bearing`, `source_specific_style_or_structure`, and `generic_deterministic_boilerplate`;
- any hash equality involving prohibited private media, notes, comments, custom XML, private slides, embedded objects, or other private content-bearing parts is a hard failure;
- generic deterministic boilerplate equality is recorded as benign equivalence, not treated as proof of copying;
- no private bytes may be copied into the reconstruction call or used as an output-package base;
- package privacy scan and lineage evidence remain mandatory.

The goal is **fresh lineage and zero prohibited private reuse**, not an unsound universal zero-equality rule.

### P3-PLAN-B5 — Private render retention is broader than necessary

The plan proposes rendering every private source slide and retaining private renders until review closure. This is inconsistent with the stated data-minimization goal when many slides may never be used for calibration/benchmarking.

Required correction:

Use a streaming/two-pass strategy:

1. profile package/geometry/style structurally for all slides without retaining render images;
2. render a slide only when required for composition classification or selected benchmark/reference review;
3. after classification, immediately delete non-selected private renders unless explicitly retained as required local review evidence;
4. retain only the minimal set of benchmark/reference renders required for the current review run;
5. record retained-count/deleted-count locally and include only aggregate sanitized counts in committed QA.

If full-deck visual classification genuinely requires rendering every slide, render sequentially, inspect, classify, and delete immediately except selected retained references.

### P3-PLAN-B6 — Fidelity claims need scope-separated statuses

The plan has a strong `professor_visual_fidelity` gate, but the acceptance semantics can still imply more coverage than the available exemplars support.

Required correction:

Define separate final statuses at minimum:

- `private_exemplar_ingestion`
- `shell_fidelity`
- `body_composition_fidelity`
- `acceptance_deck_visual_fidelity`
- `fishbone_visual_fidelity`
- `archetype_library_calibration_coverage`
- `native_powerpoint_acceptance`
- `production_group_meeting_ready`

A specific acceptance deck may pass while some unused archetypes remain provisional/insufficient. In that case do not report the whole archetype library as professor-calibrated.

The implementation report and `phase3-report-facts` schema must preserve this distinction.

## Additional required planning refinements

- Add a capability-preflight checkpoint before the private visual-classification step.
- Add a reconstruction-lineage test that proves the fresh builder entrypoint accepts sanitized descriptors only.
- Add representative-vs-stress benchmark selection tests.
- Add evidence-tier tests for one-slide versus recurring archetype evidence.
- Add private-render retention/minimization tests.
- Recalculate the planned RED-test inventory instead of preserving the current number 116 if these new tests increase it. Test count is descriptive, not a target to protect.
- Do not weaken any P3P-1–P3P-8 condition or approved Phase 1–2 invariant.

## Reviewer acceptance criteria for the revised plan

The revised plan is approvable when it demonstrates:

1. runtime image review is capability-driven and safely blockable;
2. one private slide cannot silently become a general professor archetype grammar;
3. reconstruction benchmarks cover representative and difficult examples;
4. package non-reuse is proven by fresh lineage and prohibited-part checks rather than universal hash inequality;
5. private render retention is minimized;
6. visual-fidelity claims are explicitly scoped;
7. the updated RED-test inventory covers each new invariant;
8. no production Phase 3 implementation has begun.

Until then, production Phase 3 implementation remains unauthorized.
