# Phase 3 — CP5-A Final Closure + CP5-B/C/D Integrated Sprint Design

## 1. Decision

The project is switching from **micro-review mode** to an **integrated milestone sprint** for the next implementation block.

The reviewer pre-authorizes one continuous implementation sprint containing four internal gates:

```text
Gate A0 — CP5-A final operation-binding closure
    ↓
Gate B  — CP5-B SVG Native Capability Registry
    ↓
Gate C  — CP5-C FigureOutputManifest + Static FigureCritic
    ↓
Gate D  — CP5-D Structured Scientific SVG Directors
    ↓
ONE external reviewer handoff
```

Codex must still validate each gate and preserve recoverable checkpoint commits, but it must **not stop for reviewer approval after A0, B, or C** when their internal gates pass. The next external review occurs after Gate D unless a fail-closed blocker is encountered.

This sprint is intentionally the transition from contract-heavy infrastructure work to visible scientific-figure production.

## 3. Fixed project constraints carried into this sprint

The sprint must preserve all previously approved architectural decisions.

### 3.1 Scientific truth and presentation history

- Ledger/materialized scientific state owns scientific truth.
- SVG, preview images, manifests, critic reports, PPTX, and browser/review state do not own scientific truth.
- Hypothesis and Problem remain distinct.
- Historical Fishbone revisions are immutable and recoverable.
- Failed/partial experiments and unresolved branches remain visible in research history.
- Professor narrative remains cumulative: Hypothesis → Problem → historical/current Fishbone → experiments/results → discussion → summary → transition.

### 3.2 Figure architecture

Structured scientific figures are specialist-owned, not generated by a single generic slide engine.

Existing repository-local specialist responsibilities remain authoritative:

- `fishbone-director`
- `mechanism-diagram-director`
- `experiment-schematic-director`
- `fabrication-process-director`
- `comparison-figure-director`
- `vector-figure-builder`
- `visual-style-governor`
- `figure-critic`
- `provenance-qa`

The CP5-D implementation must maintain separate director contracts/code paths so that Fishbone, mechanism, experiment setup, fabrication chronology, and comparison semantics cannot silently collapse into one generic diagram function.

### 3.3 SVG-first and evidence boundaries

- Canonical Scientific SVG remains the structured visual authoring IR.
- AI-generated imagery cannot satisfy empirical Observation/evidence bindings.
- Experimental evidence, quantitative results, real photos, and literature figures remain non-generative routes.
- CP5-D contains structured vector directors only; CP5-E owns plot/photo/literature/image-matrix/non-evidence concept routes.

### 3.4 Professor visual grammar

- CP3 `VSP003` remains the style authority available to this sprint.
- Professor-derived recurring tokens may be consumed directly.
- Professor-derived provisional tokens may be consumed only with explicit provisional provenance.
- Unresolved material-semantic colors must never be invented.
- A structured figure that does not semantically require a material color may use neutral/emphasis style tokens and explicitly state that material-semantic colors were not consumed.
- CP5-D previews are not professor-calibration PASS evidence. CP5-G owns professor calibration.

### 3.5 PowerPoint backend

- `PythonPptxAssembler` remains the sole public PPTX backend.
- CP5-B/C/D do not introduce another exporter.
- CP5-H is the first checkpoint allowed to implement an internal SVG→DrawingML adapter.
- No PPTX is produced in this integrated sprint.

### 3.6 Private data

- No private exemplar/source/render access is authorized.
- Existing sanitized CP2/CP3 artifacts may be consumed.
- Private alias/source/render counters remain `0 / 0 / 0`.
- Existing caller-supplied ephemeral privacy-scanner boundary behavior may be used for final repository/staged privacy QA, but private source files must not be opened.

## 4. Integrated sprint execution model

### 4.1 Internal gates, not micro-review stops

Each internal gate must have:

- focused RED→GREEN tests;
- schema validation for new contracts;
- candidate/component hashing;
- execution evidence;
- a checkpoint commit;
- push and remote verification where feasible;
- a durable local completion record so an execution-session usage limit does not force re-running a completed gate.

However, after a passing Gate A0, B, or C, Codex continues automatically to the next authorized gate.

### 4.2 Stop only on real blockers

Codex stops before Gate D completion only when one of these occurs:

- a gate test remains failing;
- candidate state cannot be proven;
- unexpected/unreviewed workspace contamination occurs;
- privacy boundaries would be violated;
- an input contract needed by the next gate is genuinely absent and cannot be produced within authorized scope;
- a repository architectural contradiction would require changing Phase 0–4 authority.

Environment/session interruption alone is not a scientific blocker. Durable evidence must be inspected before re-running work.

### 4.3 Checkpoint commit strategy

Expected checkpoint commits:

1. `phase3: finalize CP5-A registered validation operation`
2. `phase3: add CP5-B SVG native capability registry`
3. `phase3: add CP5-C static figure approval gate`
4. `phase3: add CP5-D structured scientific SVG directors`

These commits may be pushed as recovery checkpoints without waiting for external review. Final sprint status remains `awaiting_review` until the reviewer audits the complete A0→D milestone.

## 5. Gate A0 — CP5-A final operation-binding closure

### 5.1 Problem

Current runner-owned sealing is good, but this pattern can still produce authoritative evidence:

```python
runner.run(lambda guard: None)
```

A successful arbitrary callback is not sufficient proof that the approved CP5-A validation operation executed.

### 5.2 Required design

Replace the arbitrary authoritative callback path with a registered/fixed CP5-A operation identity.

Preferred form:

```text
Cp5aExecutionRunner
→ operation_id = CP5A_STATIC_VALIDATION_V1
→ runner internally invokes registered implementation
→ deterministic operation result
→ operation result hash
→ runner-owned private-access evidence
→ artifact finalization
```

Equivalent fixed-method APIs are acceptable, e.g. `run_cp5a_static_validation(...)`, provided callers cannot substitute an arbitrary no-op.

The evidence record must include at least:

- `operation_id`
- `operation_status`
- `operation_result_hash`
- `validation_executed`
- execution/run/candidate identity
- private attempt counters
- runner-owned/sealed identity

The registered operation must execute real synthetic CP5-A validation. At minimum it must validate the CP5-A synthetic corpus and the frozen CP4 plan/spec contract set used by CP5-A. The exact implementation may reuse existing validation functions; it must not create another scientific source of truth.

### 5.3 Gate A0 tests

Required negatives:

- arbitrary `lambda _: None` cannot create authoritative evidence;
- unknown operation ID fails;
- operation result mutation/hash mismatch fails;
- wrong candidate/run identity fails;
- registered operation exception yields no completed evidence;
- any guarded private attempt fails.

Required positive:

- registered CP5-A operation executes;
- operation result is non-empty/deterministic;
- result hash is bound into evidence;
- final private counters remain zero;
- final artifact QA accepts the runner-owned record.

After Gate A0 passes, CP5-A is frozen for this sprint. Do not reopen SVG-language feature design during B/C/D.

## 6. Gate B — CP5-B SVG Native Capability Registry

### 6.1 Purpose

CP5-B answers a different question from CP5-A:

> A Scientific SVG feature may be legal in the canonical IR; what is the current, evidence-backed truth about later PowerPoint/native compilation?

SVG legality and native compilation capability remain independent.

### 6.2 Required states

Every registry capability record uses exactly one native state:

- `NATIVE_EXACT`
- `NATIVE_NORMALIZED`
- `VECTOR_FALLBACK`
- `RASTER_FALLBACK`
- `UNSUPPORTED`
- `UNKNOWN`

Every state is paired with an evidence level:

- `upstream_declared`
- `source_inspected`
- `thesis_synthetic_verified`
- `native_powerpoint_verified`

Native `UNKNOWN` is honest and non-failing for a legal Scientific SVG feature.

`UNSUPPORTED` means native compilation is unavailable/forbidden, not that the Scientific SVG itself is invalid.

Silent raster fallback is forbidden.

### 6.3 Feature granularity

Do not model capability only as one record per SVG element. Native behavior can depend on attributes/semantics.

Registry coverage must include the CP5-A language at feature level, including at least:

- root SVG/viewBox;
- groups;
- rect/circle/ellipse;
- line/polyline/polygon;
- the supported path-command subset;
- text;
- tspan/editable mixed CJK/Latin text;
- image;
- marker/local marker references;
- clipPath/local clip references;
- translate/scale/rotate/matrix transforms;
- stroke width/cap/join/dash;
- fill/stroke opacity;
- text anchor/baseline/font attributes;
- local same-document reference behavior;
- SVG-as-vector fallback capability where existing thesis evidence supports it.

Each feature receives a stable feature ID and registry version.

### 6.4 Evidence discipline

- Source inspection/upstream documentation cannot by itself promote a thesis capability to `NATIVE_EXACT` or `NATIVE_NORMALIZED`.
- Existing committed Phase 1 evidence of an actual SVG relationship may support only the narrowly proven vector-fallback statement, not editable native DrawingML semantics.
- Native PowerPoint unavailable → corresponding evidence remains absent; do not block CP5-C/D because of it.
- Do not implement the DrawingML compiler in Gate B.

### 6.5 Gate B artifacts

At minimum:

- `svg-native-capability-registry.json`
- `svg-native-test-vectors.json`
- schema(s) for registry, records, and vectors
- `checkpoint-5b-execution-evidence.json`
- `checkpoint-5b-qa.json`

Synthetic vectors must exercise the legal CP5-A feature set and must be canonical Scientific SVG.

## 7. Gate C — CP5-C FigureOutputManifest + Static FigureCritic

### 7.1 Purpose

CP5-C creates the mandatory gate between raw/generated figure output and downstream layout.

Required pipeline:

```text
ScientificFigureSpec
→ canonical Scientific SVG/source asset
→ FigureOutputManifest
→ Static FigureCritic
→ APPROVED_FIGURE | FAIL | BLOCKED
→ Layout only when APPROVED_FIGURE
```

A director or vector builder may never hand a raw figure directly to Layout.

### 7.2 FigureOutputManifest

The canonical manifest must bind at least:

- figure ID and figure revision;
- ScientificFigureSpec ref/hash;
- FigureProductionPlan ref/hash;
- output kind;
- canonical SVG/source artifact ref/hash;
- Scientific SVG profile/version;
- CP5-B capability registry ID/version;
- used feature IDs and capability records;
- declared fallback, if any;
- source/evidence/provenance refs outside SVG;
- style profile/style-resolution refs;
- privacy/lineage state;
- static critic ref/status;
- downstream handoff state.

It must not duplicate scientific truth beyond validated references.

### 7.3 Static FigureCritic

Static critic must execute real checks, including:

- ScientificFigureSpec validity and route consistency;
- SVG profile/static QA validity;
- manifest/spec/SVG figure identity consistency;
- hashes match physical artifacts;
- every used SVG/native feature has a CP5-B registry record;
- fallback is explicit and permitted;
- native `UNKNOWN` or native `UNSUPPORTED` alone does not fail legal SVG;
- scientific/evidence boundary is respected;
- style tokens are provenance-bound;
- no private leakage;
- no raw/unapproved figure can hand off to Layout.

Status semantics:

- `APPROVED_FIGURE`: all required static checks pass.
- `FAIL`: actual contract/identity/provenance/static error.
- `BLOCKED`: required external/source input is absent but no false scientific/visual statement is made.

### 7.4 Gate C artifacts

At minimum:

- FigureOutputManifest schema
- Static FigureCritic report schema
- APPROVED_FIGURE identity schema
- checkpoint-5c QA/evidence artifacts
- synthetic positive and negative manifests
- graph/handoff audit proving Layout requires APPROVED_FIGURE.

## 8. Gate D — CP5-D Structured Scientific SVG Directors

Gate D should complete the structured-director checkpoint rather than only a partial demonstration.

Required director families:

1. Fishbone
2. Mechanism
3. Experiment Schematic
4. Fabrication / Process
5. Fair Comparison

Each family must remain a separate specialist implementation path and must route through the shared CP5-A/B/C infrastructure.

### 8.1 Director-specific typed payloads

The CP4 `ScientificFigureSpec` remains the top-level route/spec authority, but its generic `specialist_payload` is not rich enough to hold all structured content.

CP5-D therefore introduces typed, versioned director-input contracts referenced by the FigureSpec/manifest, without changing scientific authority.

Required contracts should include equivalent information to the following.

#### Fishbone input

- fishbone ID/revision
- historical cursor/revision refs
- stable branch IDs
- parent refs
- branch labels/status (`completed`, `partial`, `failed`, `future`, etc.)
- focus branch ref
- immutable prior revision hashes
- optional branch notes only when source-bound

Required semantics:

- stable hierarchy;
- no branch renumbering;
- no orphan/cycle;
- current focus visually prominent;
- previous revision remains byte/hash immutable;
- completed/partial/failed/future branches remain visible.

#### Mechanism input

- causal nodes
- directed relations
- known/unknown/uncertain relation state
- alternative mechanism branches where present
- claim/evidence refs outside SVG
- explicit uncertainty labels

Required semantics:

- do not infer certainty;
- do not absorb fabrication chronology;
- do not replace empirical evidence;
- unknowns remain visible.

#### Experiment schematic input

- sample/system components
- independent/dependent/control variables where applicable
- controls
- instrumentation
- measurement points
- input/output signal/material flow
- labels and stage/method refs

Required semantics:

- controls cannot disappear;
- measurement points remain explicit;
- no invented instrument/condition;
- fabrication chronology stays out of this diagram.

#### Fabrication/process input

- ordered process steps
- material/state refs
- state transitions
- known/unknown conditions
- source/provenance refs

Required semantics:

- chronological order is preserved;
- unknown temperature/time/condition remains `UNKNOWN`;
- no invented process parameter;
- mechanism and measurement setup remain separate.

#### Fair comparison input

- compared sides/groups
- common comparison dimensions
- explicit control/proposed/baseline labels
- scale/normalization policy
- shared metrics/criteria

Required semantics:

- matched scale and comparable visual weight;
- no side is visually advantaged by hidden scale changes;
- missing information stays explicit;
- comparison does not fabricate quantitative difference.

### 8.2 Shared vector builder

`vector-figure-builder` may provide geometry primitives and deterministic SVG construction, but it must not own director scientific semantics.

Each director must create its own typed intermediate layout/semantic plan before passing declared primitives to the shared builder.

No single catch-all `make_diagram(kind=...)` implementation may substitute for the specialist boundaries.

### 8.3 Style integration

Directors consume CP3 `VSP003` through `visual-style-governor`.

Each output must persist token provenance:

- recurring professor-derived;
- provisional professor-derived;
- fallback;
- unresolved/not consumed.

Material-semantic color must never be inferred from generic emphasis color. When material color is unnecessary, record `material_semantic_colors_not_consumed=true` or equivalent rather than blocking the whole structured figure.

### 8.4 Acceptance fixtures

Use only committed, non-private sources.

Preferred inputs:

- existing CP4 Figure Plans/ScientificFigureSpecs;
- Phase 2 committed synthetic Fishbone history and materialized scientific-state fixtures;
- new clearly synthetic structured fixtures where existing committed state is insufficient.

Do not convert private exemplars or real thesis source data into CP5-D fixtures.

For each of the five director families, produce at least:

- one representative acceptance fixture;
- one stress/edge fixture or negative mutation family.

Fishbone must include an actual revision/history case, preferably linked to the existing committed Phase 2 FB001 fixture family.

### 8.5 Required visible outputs

To make this sprint visually reviewable, produce non-authoritative preview renders when a deterministic SVG renderer is available.

At minimum target:

- representative Fishbone SVG + PNG preview
- representative Mechanism SVG + PNG preview
- representative Experiment Schematic SVG + PNG preview
- representative Fabrication/Process SVG + PNG preview
- representative Fair Comparison SVG + PNG preview
- one `structured-director-montage.png`

These PNGs are **review previews only**. They are not CP5-F render-critic or professor-calibration evidence.

If preview rendering is unavailable, record `preview_render_blocked_environment`; do not falsely mark CP5-F or visual fidelity as passed.

### 8.6 Gate D handoff

Every representative director output must complete:

```text
director input
→ ScientificFigureSpec binding
→ canonical Scientific SVG
→ FigureOutputManifest
→ Static FigureCritic
→ APPROVED_FIGURE
```

No PPTX or slide assembly occurs.

## 10. Validation and performance strategy

The goal is fewer external review loops, not weaker QA.

### 10.1 Per-gate validation

Each internal gate runs its focused suite and relevant schema/contract checks.

Do **not** run the full repository regression after every small correction.

### 10.2 Definitive final regression

After Gate D candidate is frozen:

- compute TESTED candidate-state hash;
- create a fresh disposable worktree;
- run the complete CP1+CP2+CP3+CP4+CP5-A+B+C+D regression;
- persist stdout/stderr/exit/pre-hash/post-hash/completion marker using the durable runner pattern;
- recompute CURRENT candidate hash independently;
- require equality and `tests_failed=0`.

### 10.3 Session interruption

Every long-running gate/final regression must use durable local evidence:

```text
PRE-HASH
→ COMMAND
→ STDOUT / STDERR
→ EXIT CODE
→ POST-HASH
→ COMPLETION MARKER
```

If a Codex execution session stops, the next session reads this evidence before deciding to rerun.
